After every implementation run, AI-Implement runs an automated review pass against the PR diff — the `post-push-review` step. Unlike the implementation pass, this one can loop: if it finds blocking issues, Claude fixes them and the review runs again, up to a configured cap. The result is either an approved, ready-to-merge PR, or a PR left open with the remaining blockers listed for a human.

## What gets posted

The step starts by posting a short "Running post-implementation review..." comment, then reviews the diff for bugs, missing requirements, unsafe behavior, and test gaps. From there:

- **No issues found** — Claude submits a PR review and posts a comment starting with `✅ Approved`, ending with **Merge readiness: Ready to merge.**
- **Blocking issues found** — Claude posts a comment starting with `⚠️ Reviewer found issues — starting fix pass`, listing each blocking issue, then fixes them and force-pushes a revision. The review runs again against the new diff.
- **Review cap reached without approval** — after the configured number of passes, Claude posts `⚠️ Reached review cap` with whatever blocking issues remain, and **Merge readiness: Not ready to merge.**

Each comment is updated in place on later passes rather than duplicated, identified by an iteration marker in the comment body.

<Note>
  The seeded `WORKFLOW.md` template still calls this "the gap analysis comment" when it tells Claude how to handle a gap-fill run — that's the informal name for whichever of the comments above is currently on the PR, not a separate feature.
</Note>

## Iteration cap and external review

The step runs up to three review passes by default, which can force-push at most two revised versions — the third pass either approves or reports the review cap without pushing again. Override the cap by replacing the `post-push-review` step; see [Custom pipeline steps](/latest/customize/custom-steps#built-in-step-ids).

Before finishing a pass, the step also waits for a configured external review provider (see `reviewProviders` in [Repo-level configuration file](/latest/customize/custom-steps#repo-level-configuration-file)) and folds any findings it reports, plus any failing CI checks on the same commit, into the same blocking-issues list.

## Model

Review runs on the same model as implementation by default — the `model` value from your `WORKFLOW.md` front matter, or `claude-sonnet-4-6` when that's unset. There is no separate, cheaper default for review.

To use a different model for review than for implementation, set `models.review` in `.ai-implement/config.yml`:

```yaml
models:
  implement: claude-opus-4-8
  review: claude-sonnet-4-6
```

See [`models.review`](/latest/customize/custom-steps#param-models-review) for details.

## Triggering another pass

After reading the review comments, you can ask Claude to address remaining blockers without starting a new implementation from scratch.

<Steps>
  <Step title="Open the PR on GitHub">
    Navigate to the pull request that AI-Implement opened.
  </Step>
  <Step title="Post the trigger comment">
    Add a comment starting with `/ai-implement` on the PR. You must have write access to the repository.

    ```
    /ai-implement
    ```

    Anything you write after the trigger is passed to Claude as an instruction for that pass, e.g. `/ai-implement also add tests for the error paths`.
  </Step>
  <Step title="Wait for the run">
    On a repo that generates the current dispatch envelope, the orchestrator's own webhook picks up the comment directly — no workflow file involved. On a repo still carrying `comment-trigger.yml` (an older repo that hasn't been re-synced), that workflow picks it up instead. Either way, a new run dispatches against the existing branch: Claude checks out the branch, reviews the latest review comment, and pushes gap-fill commits directly to the PR.
  </Step>
</Steps>

The issue link, identifier, and description are all preserved from the original run — Claude sees the same ticket context it had during the first pass.

<Warning>
The `/ai-implement` trigger only works on PRs opened by AI-Implement. PRs created by hand do not contain the metadata block the trigger reads, so it posts a warning comment and exits without dispatching. On an envelope repo, the trigger also requires the GitHub App to be subscribed to comment events and a shared webhook secret configured on both sides — see [`GITHUB_WEBHOOK_SECRET`](/latest/configuration/environment-variables#param-github-webhook-secret).
</Warning>

<Tip>
You can run `/ai-implement` multiple times on the same PR. Each pass updates the existing review comment in place, so you can track progress without a growing thread of duplicate comments.
</Tip>
