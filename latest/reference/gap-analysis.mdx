After every implementation run opens a PR, AI-Implement runs a second Claude pass — using the same model as the implementation pass — that reviews the diff for correctness and decides whether it's ready to merge. It's based only on the PR diff and the original ticket; Claude does not explore the broader codebase during this pass.

<Note>
This pass only runs when the implementation step succeeds and an open PR is found on the branch. If Claude does not open a PR during the implementation run, no review pass runs.
</Note>

## How the review pass works

The reviewer sets `approved=true` only when no further code changes are needed. Otherwise, it lists every blocking issue it found, and the step:

1. Posts a PR comment with the blocking issues and a **Merge readiness: Not ready to merge** line.
2. Pushes a fix commit (force-pushed to the same branch) addressing them.
3. Reviews the updated diff again.

This repeats for up to 3 passes by default, force-pushing at most 2 revisions — the third pass reports the outcome without pushing again. The cap is configurable only by overriding the `feedback-loop` step (see [Add custom pipeline steps](/latest/customize/custom-steps#built-in-step-ids)); there's no config-file setting for it.

Each pass also submits a native GitHub PR review (approve, or request changes with the blocking issues) alongside its comment.

<Tabs>
  <Tab title="Approved">
    The PR comment reads **✅ Approved (N iterations)** with **Merge readiness: Ready to merge**, and the native PR review is an approval.
  </Tab>
  <Tab title="Review cap reached">
    The final PR comment reads **⚠️ Reached review cap (N iterations) without approval**, lists what's still unresolved, and reads **Merge readiness: Not ready to merge**. The PR is left open for a human to finish — no further automated passes run on this dispatch.
  </Tab>
</Tabs>

<Tip>
  To make this pass wait for an external review bot's findings first and fold them into its own review, configure `reviewProviders` in `.ai-implement/config.yml` — see [Repo-level configuration file](/latest/customize/custom-steps#repo-level-configuration-file). By default it waits for a check matching one of several recognized review-bot names.
</Tip>

## Triggering another pass

After reviewing the PR, you can ask Claude to address the remaining items without starting a new implementation from scratch.

<Steps>
  <Step title="Open the PR on GitHub">
    Navigate to the pull request that AI-Implement opened.
  </Step>
  <Step title="Post the trigger comment">
    Add a comment that **starts with** `/ai-implement` on the PR. You must be a collaborator with write access (or `maintain`/`admin`) on the repository.

    ```
    /ai-implement
    ```

    Anything you write after the trigger is passed to Claude as an instruction for that run — for example `/ai-implement also add tests for the error paths`. Leave it bare to let Claude work from the review findings alone.
  </Step>
  <Step title="Wait for the run">
    The orchestrator's own GitHub webhook receives the comment directly and dispatches a gap-fill run against the existing branch — no workflow file in the target repo is involved. Claude checks out the branch, reviews the previous findings, and pushes gap-fill commits directly to the PR.

    <Warning>
      This requires a working orchestrator webhook: `GITHUB_WEBHOOK_SECRET` configured on the orchestrator, the GitHub App subscribed to the **Issue comment** event, and the orchestrator reachable from the public internet. Without it, commenting `/ai-implement` does nothing. See [Configure webhook delivery](/latest/setup/github-app#create-the-github-app) and [`GITHUB_WEBHOOK_SECRET`](/latest/configuration/environment-variables#param-github-webhook-secret).
    </Warning>
  </Step>
</Steps>

The issue link, issue identifier, and issue description are all preserved from the original run — Claude sees the same ticket context it had during the first pass.

<Warning>
The `/ai-implement` trigger only works on PRs opened by AI-Implement. PRs created by hand do not carry the metadata the trigger reads, so it is silently ignored.
</Warning>
