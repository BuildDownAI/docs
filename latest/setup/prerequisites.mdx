Before you install AI-Implement, gather everything in the checklist below. Each item maps to a later setup step, so having them ready in advance makes the process significantly smoother.

<Steps>
  <Step title="Linear or Jira workspace">
    <Tabs>
      <Tab title="Linear">
        You need a Linear workspace where you can create labels. AI-Implement relies on the `AI-Implement` label to identify issues to process. You do not need admin access to the workspace — member-level access with the ability to create labels is sufficient.
      </Tab>

      <Tab title="Jira">
        You need an Atlassian Jira Cloud workspace where you can create custom select fields. AI-Implement requires two custom fields (`AI-Implement Status` and `AI-Implement Repo`) to identify and route issues, plus permission to add them to your project's issue screens.
        
        <Info>
          See [Jira manual setup](/latest/setup/target-repo#jira-manual-custom-field-setup) for the full custom-field walkthrough; you'll do that during the target-repo connection step.
        </Info>
      </Tab>
    </Tabs>
  </Step>

  <Step title="GitHub organization or account, and a GitHub App you control">
    AI-Implement uses a GitHub App to authenticate workflow dispatches and to open pull requests under the app's identity (which is what allows the `/ai-implement` comment trigger to work correctly). You need either:

    - A GitHub organization where you can create a GitHub App, or
    - A personal GitHub account with the ability to create a GitHub App

    You will create the App during setup. See [Create a GitHub App](/latest/setup/github-app) for the full walkthrough.
  </Step>

  <Step title="Somewhere to run the orchestrator">
    The orchestrator is a small Node.js service. You have two options:

    <Columns cols={2}>
      <Card title="Fly.io (recommended)" icon="cloud">
        A Fly.io account lets you deploy the orchestrator as a managed app. The supplied deployment uses a `shared-cpu-1x` machine with 2 GB of memory. See [Deploy the orchestrator](/latest/setup/deploy) for instructions.
      </Card>
      <Card title="Any server running Node.js" icon="server">
        You can run the orchestrator on any server or local machine that has Node.js 24.x installed. The local development workflow is covered in [Deploy the orchestrator](/latest/setup/deploy).
      </Card>
    </Columns>
  </Step>

  <Step title="Choose model access">
    For Codex, use an OpenAI API key or connect your own ChatGPT plan on **Models & providers**. Follow [Use Codex with OpenAI](/latest/providers/openai) after creating your project mapping. A configured project that uses Codex for every stage does not need an Anthropic credential.

    A connected ChatGPT plan is for personal and self-hosted use of your own account. Hosted subscription runs also require a private or internal repository authorized for subscription testing. See the [Codex guide](/latest/providers/openai) for the connection and readiness checks.

    If you keep a project on legacy Claude behavior, choose one of these credential paths:

    | Provider | What you need |
    |---|---|
    | Anthropic API (fallback) | An `ANTHROPIC_API_KEY` from [console.anthropic.com](https://console.anthropic.com) |
    | Claude Code OAuth (preferred) | A `CLAUDE_CODE_OAUTH_TOKEN` — preferred over the API key when both are present |
    | AWS Bedrock | An AWS account with Bedrock access and an IAM role configured for GitHub OIDC |

    <Note>
      These repository secrets apply to legacy Claude projects. Configured projects select a managed account profile for each stage; see [Agent settings per stage](/latest/configuration/agents).
    </Note>
  </Step>

  <Step title="A compatible runner and synced workflows">
    The Codex setup path uses GitHub Actions with a compatible runner image and current workflow templates. Merge the workflow pull request from project creation before opting in. For an existing project, use **Sync workflows** on **Projects** and merge that pull request first.

    See [Runner images](/latest/customize/runner-image) for compatibility checks. Managed post-push review-fix support also requires a healthy Restate connection; [Managed review-fix](/latest/reference/post-push-review#managed-review-fix-with-codex) describes the supported backend and remaining live-validation limits.
  </Step>

  <Step title="Node.js 24.x (for local development)">
    If you plan to run the orchestrator locally or contribute to the codebase, you need Node.js 24.x installed on your machine. For production Fly.io deployments, Node.js is included in the build — you do not need to install it separately.
  </Step>
</Steps>
