`PLANNING.md` supplies the planning prompt for Claude or Codex. The planning run renders it, reads the codebase, and writes comments for the orchestrator to post to your issue.

Choose the agent and execution settings in [Agent settings per stage](/latest/configuration/agents). Changing prompt text does not switch agents. The workflow remains `claude-plan.yml`.

## File structure

Like `WORKFLOW.md`, `PLANNING.md` has two parts:

**YAML front matter** (between the `---` lines at the top) — read by the workflow to configure the run. Stripped before the agent sees the prompt.

**Markdown body** — everything after the front matter. A fixed list of variables is substituted into it, and the result is sent to the planning agent.

## Front matter keys

<AccordionGroup>
  <Accordion title="model">
    Selects the planning model for legacy projects. Configured projects use the planning stage model instead; see [Agent settings per stage](/latest/configuration/agents).

    ```yaml
    # Anthropic API or OAuth
    model: claude-sonnet-4-6

    # AWS Bedrock (replace with your model ID or inference-profile ARN)
    model: anthropic.claude-sonnet-4-6-20250805-v1:0
    ```

    For a legacy Bedrock project, supply a compatible Bedrock model ID or inference-profile ARN. Omitting it can fall back to an Anthropic model ID that Bedrock cannot use.
  </Accordion>
</AccordionGroup>

## Variables available in the body

The variables below are substituted into the body by a regular expression, not by `envsubst`. Reference any of them anywhere in the body.

<Note>
  Only `${NAME}` forms are substituted, and a token that is not on this list is treated differently than shell semantics would suggest. [Workflow template files](/latest/configuration/workflow-templates) covers the rules and what they mean for a shell example in your body.
</Note>

| Variable | Description |
|---|---|
| `${ISSUE_IDENTIFIER}` | Ticketing-system identifier — `ENG-42` for Linear, `PROJ-42` for Jira |
| `${ISSUE_TITLE}` | Issue title |
| `${ISSUE_DESCRIPTION}` | Full issue description (Markdown) |
| `${ISSUE_ID}` | Issue UUID — used in API calls to post comments |
| `${PARENT}` | Parent issue as `- IDENTIFIER: Title`, or `None` |
| `${SIBLINGS}` | Sibling stories (other children of the same parent), newline-separated, or `None` |
| `${DEPENDENCIES}` | Related issues as `- [type] IDENTIFIER: Title`, newline-separated, or `None` |

## Planning comment format

The supplied template asks the planner to write the files below. Keep their exact headers so implementation and review can find the right context.

### Implementation Map

File: `ai-output/comments/01-implementation-map.md`

Header: `## 🗺 AI Planning: Implementation Map`

Keep the map within 60 lines. Include:

- **Approach** — a short description of the existing pattern and the change.
- **Files** — paths with the verbs Create, Modify, Test, or Delete.
- **Constraints** — relevant ordering or shared-file constraints.

For example:

```markdown
- Modify: `src/api/export.ts`
- Test: `tests/export.test.ts`
```

Keep the template's instructions for the planning metadata at the end of the map. It lists the complete file set and the change's risk level. The implementation run uses the map as reference context.

### Acceptance Bar

File: `ai-output/comments/02-acceptance-bar.md`

Header: `## ✅ AI Planning: Acceptance Bar`

List testable claims covering the acceptance criteria. For each claim, name the behavior and how to check it. Include material edge cases. The reviewer uses this comment to assess the result.

### Risks & Open Questions

File: `ai-output/comments/03-risks.md`

Header: `## ⚠️ AI Planning: Risks & Open Questions`

Record material uncertainties, prerequisites, and easily missed behavior. If none exist, say so in one sentence.

<Note>
  Sync preserves existing `PLANNING.md` files. Older templates can still ask for Architecture Analysis or Test Plan comments. Edit an existing template deliberately; a workflow sync does not replace its output instructions.
</Note>

## Codex planning limits

Codex planning can read and search repository text. It can write planning comments under `ai-output/comments/`. It cannot change source files, run commands, delegate work, or use network tools.

Keep instructions within those capabilities. Put executable setup and validation in the implementation workflow's [hooks](/latest/customize/workflow-md#front-matter-keys).

## Customizing the "Repo context" section

The `## Repo context` section is where you point the planning agent at the right parts of your codebase and establish the conventions that matter for architectural decisions.

```markdown
## Repo context

- **Stack:** Node.js 20, TypeScript 5, PostgreSQL 16, Prisma ORM, Vitest
- **Key conventions:**
  - All database access goes through the repository layer in `src/repositories/`
  - API routes live in `src/api/routes/`; middleware in `src/api/middleware/`
  - Avoid introducing new dependencies without good reason
- **Areas to always check:** `src/models/`, `src/api/`, `migrations/`
```

<Tip>
  Use the **Areas to always check** field to direct the planning agent to the directories most likely to be relevant for any given issue. This reduces analysis time and keeps the architecture comments grounded in your actual code structure rather than generic advice.
</Tip>

## Example: adding analysis prompts

You can add repo-specific analysis instructions anywhere in the body. For example, to always have the planner check the migration directory when database changes are involved:

```markdown
## Repo context

- **Areas to always check:** `src/models/`, `src/api/`, `migrations/`
- If the issue involves data changes, check `migrations/` for the latest schema
  and assess whether a new migration is needed.
```

<Note>
  The sync workflow seeds `PLANNING.md` into your repo once and never overwrites it. Every change you make is permanent — future syncs will not touch this file.
</Note>
