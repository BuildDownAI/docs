`PLANNING.md` controls what Claude does during the planning phase — it reads the codebase and posts structured architecture analysis, test plan, work units, and cross-story comments back to your ticketing system. When the planning workflow (`claude-plan.yml`) runs for an issue, it renders this file and sends the result to Claude. Claude then explores the repo and writes structured planning comments back to the issue — without creating any branches, files, or pull requests.

## File structure

Like `WORKFLOW.md`, `PLANNING.md` has two parts:

**YAML front matter** (between the `---` lines at the top) — read by the workflow to configure the run. Stripped before Claude sees anything.

**Markdown body** — everything after the front matter. The runner substitutes the variables below into it — not with the `envsubst` utility, but with its own fixed-token substitution — and sends the result to Claude as the prompt. This body **replaces** the runner's built-in planning prompt rather than adding to it, so anything the built-in prompt would have said must be stated here.

## Front matter keys

<AccordionGroup>
  <Accordion title="model">
    The model ID passed to `claude-code --model`. Accepts any ID your configured provider supports.

    ```yaml
    # Anthropic API or OAuth
    model: claude-sonnet-4-6

    # AWS Bedrock (replace with your model ID or inference-profile ARN)
    model: anthropic.claude-sonnet-4-6-20250805-v1:0
    ```

    This key is **required when using Bedrock**. There is no Bedrock-specific default — the model resolves from a single provider-agnostic chain that ends in `claude-sonnet-4-6`.

    Omit it on a Bedrock-mapped repo and that Anthropic model ID is substituted silently. It is invalid on Bedrock, so the run fails when the model is invoked rather than up front.

    For the Anthropic provider, `claude-sonnet-4-6` is the intended default and omitting the key is safe.
  </Accordion>
</AccordionGroup>

## Variables available in the body

The runner substitutes these `${UPPER_SNAKE}` tokens into the body via a fixed-token regular expression, not the `envsubst` utility — any other `${TOKEN}`-shaped text is replaced with an empty string. You can reference any of the variables below anywhere in the body:

| Variable | Description |
|---|---|
| `${ISSUE_IDENTIFIER}` | Ticketing-system identifier — `ENG-42` for Linear, `PROJ-42` for Jira |
| `${ISSUE_TITLE}` | Issue title |
| `${ISSUE_DESCRIPTION}` | Full issue description (Markdown) |
| `${ISSUE_ID}` | Ticket UUID. Rarely useful — the runner holds no ticketing credential, so it can't call the ticketing API directly; posting back to the ticket goes through the `ai-output/comments/` file convention instead. |
| `${PARENT}` | Parent issue as `- IDENTIFIER: Title`, or `None` |
| `${SIBLINGS}` | Sibling stories (other children of the same parent), newline-separated, or `None` |
| `${DEPENDENCIES}` | Related issues as `- [type] IDENTIFIER: Title`, newline-separated, or `None` |

## Comment types Claude must post

Claude writes exactly three structured comment files under `ai-output/comments/`, which the orchestrator posts to the ticket after the run. The filenames and headers are exact strings the implementer and the dispatch guard parse, so do not change them.

<Steps>
  <Step title="Implementation Map">
    Filename: `ai-output/comments/01-implementation-map.md`. Header: `## 🗺 AI Planning: Implementation Map`. Consumer: the implementer.

    Required content, no more than 60 lines total:

    - **Approach** — at most 3 sentences describing the implementation strategy
    - **Files** — canonical verb bullets the implementer and the dispatch guard both parse:

      ```markdown
      ## Files
      - Create: `src/new-module.ts`
      - Modify: `src/existing.ts`
      - Test: `src/__tests__/existing.test.ts`
      - Delete: `src/old-module.ts`
      ```

      Use exactly one of `Create`, `Modify`, `Test`, or `Delete` per line, with the path backtick-quoted.
    - **Constraints & Hazards** — repo-discovered load-bearing tests, generated files, migration order constraints, or integration seams the implementer must not break. If `${DEPENDENCIES}`, `${SIBLINGS}`, or `${PARENT}` is not `None`, fold any cross-story coordination notes here — there is no separate cross-story comment.

    The comment ends with a machine-readable block, with the `files` array and `risk` value filled in:

    ```
    <!-- ai-implement-planning
    v: 1
    files: ["src/a.ts", "src/b.ts"]
    risk: low|medium|high
    -->
    ```
  </Step>

  <Step title="Acceptance Bar">
    Filename: `ai-output/comments/02-acceptance-bar.md`. Header: `## ✅ AI Planning: Acceptance Bar`. Consumer: the reviewer.

    A numbered list of falsifiable claims — each one directly checkable against the diff or by running a specific command. Generic test enumerations like "all tests pass" don't count as a claim.
  </Step>

  <Step title="Risks & Open Questions">
    Filename: `ai-output/comments/03-risks.md`. Header: `## ⚠️ AI Planning: Risks & Open Questions`. Consumer: the implementer and reviewer.

    Edge cases, unknowns, and potential problems discovered during codebase exploration, grounded in what was actually found rather than generic boilerplate.
  </Step>
</Steps>

<Note>
  Do not post comments directly to Linear or Jira from this workflow. The orchestrator reads the `.md` files written under `ai-output/comments/` and posts each one after the run completes.
</Note>

## Customizing the "Repo context" section

The `## Repo context` section is where you point Claude at the right parts of your codebase and establish the conventions that matter for architectural decisions.

```markdown
## Repo context

- **Stack:** Node.js 20, TypeScript 5, PostgreSQL 16, Prisma ORM, Vitest
- **Key conventions:**
  - All database access goes through the repository layer in `src/repositories/`
  - API routes live in `src/api/routes/`; middleware in `src/api/middleware/`
  - Avoid introducing new dependencies without good reason
- **Areas to always check:** `src/models/`, `src/api/`, `migrations/`
```

<Tip>
  Use the **Areas to always check** field to direct Claude to the directories most likely to be relevant for any given issue. This reduces analysis time and keeps the architecture comments grounded in your actual code structure rather than generic advice.
</Tip>

## Example: adding analysis prompts

You can add repo-specific analysis instructions anywhere in the body. For example, to always have Claude check the migration directory when database changes are involved:

```markdown
## Repo context

- **Areas to always check:** `src/models/`, `src/api/`, `migrations/`
- If the issue involves data changes, check `migrations/` for the latest schema
  and assess whether a new migration is needed.
```

<Note>
  The sync workflow seeds `PLANNING.md` into your repo once and never overwrites it. Every change you make is permanent — future syncs will not touch this file.
</Note>
