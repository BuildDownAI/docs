This guide walks you through running AI-Implement for the first time. By the end, you'll have the orchestrator running locally, a target repo connected, and a Linear issue on its way to becoming a pull request.

<Note>
  Before you start, make sure you have: a Linear or Jira workspace with API access, a GitHub App you control, Node.js 24.x, and model access for your selected agent. Codex uses a managed OpenAI profile; legacy Claude projects use their existing provider credentials. See [Prerequisites](/latest/setup/prerequisites) for details on setting each one up.
</Note>

<Steps>

  <Step title="Clone the repository">
    Clone AI-Implement and move into the project directory:

    ```bash
    git clone https://github.com/BuildDownAI/AI-Implement.git
    cd AI-Implement
    ```
  </Step>

  <Step title="Configure your environment">
    Copy the example environment file and fill in your credentials:

    ```bash
    cp .env.example .env
    ```

    Open `.env` and set at minimum:

    <Tabs>
      <Tab title="Linear">
        | Variable | Description |
        |---|---|
        | `LINEAR_CLIENT_ID` | Client ID of your Linear application |
        | `LINEAR_CLIENT_SECRET` | Client secret for the same application |
        | `GITHUB_APP_ID` | The numeric ID of your GitHub App |
        | `GITHUB_APP_PRIVATE_KEY` | Your GitHub App's RSA private key in PEM format, with newlines escaped as `\n` |

        See [Create a Linear app](/latest/setup/linear-app) if you haven't created one yet.
      </Tab>

      <Tab title="Jira">
        | Variable | Description |
        |---|---|
        | `JIRA_EMAIL` | Your Atlassian account email — selects Basic auth, the recommended mode |
        | `JIRA_TOKEN` | Your Atlassian API token (create from Atlassian → Security → API tokens) |
        | `JIRA_SITE_URL` | Your Atlassian site URL, e.g. `https://acme.atlassian.net` |
        | `GITHUB_APP_ID` | The numeric ID of your GitHub App |
        | `GITHUB_APP_PRIVATE_KEY` | Your GitHub App's RSA private key in PEM format, with newlines escaped as `\n` |

        To use OAuth instead, leave `JIRA_EMAIL` blank and set `JIRA_CLOUD_ID`.
      </Tab>
    </Tabs>


    For the Codex path, also set these orchestrator values:

    | Variable | Description |
    |---|---|
    | `ADMIN_ACCESS_CODE` | A non-empty access code for the admin UI, unless you configure sign-in |
    | `RUNNER_TOKEN_SECRET` | A stable secret for callback tokens and encrypted model credentials; keep it unchanged across restarts |
    | `RUNNER_CALLBACK_BASE_URL` | The orchestrator's public HTTPS base URL, reachable from GitHub Actions |

    A GitHub-hosted job cannot call back to `localhost`. Expose your local orchestrator through a reachable HTTPS URL, or [deploy a persistent orchestrator](/latest/setup/deploy). Planning refuses dispatch without the callback URL and secret.

    These settings are optional for a first run:

    | Variable | Default | Description |
    |---|---|---|
    | `NOTIFY_TYPE` | `slack` | Notification provider: `slack` or `teams` |
    | `NOTIFY_WEBHOOK_URL` | _(none)_ | Webhook URL — notifications are skipped if unset |
    | `POLL_INTERVAL_MS` | `60000` | How often the orchestrator polls for new issues, in milliseconds |
    | `PORT` | `8080` | HTTP port for the orchestrator and admin UI |
    | `DEDUP_DB_PATH` | `./dedup.sqlite` | Path for the SQLite database |

    <Tip>
      Set `ADMIN_ACCESS_CODE` to a non-empty value so you can reach the admin UI at the project mapping step. It's the quickest option for a first run; [admin sign-in](/latest/setup/sso) is the better fit once you deploy.
    </Tip>
  </Step>

  <Step title="Add required secrets to the target repo">
    In the target repo's **Settings → Secrets and variables → Actions**, add these org or repo secrets:

    | Secret | Value |
    |---|---|
    | `AI_IMPLEMENT_APP_ID` | Your GitHub App's numeric ID |
    | `AI_IMPLEMENT_PRIVATE_KEY` | Your GitHub App's PEM private key |

    These GitHub App secrets are shared by both agent paths.

    For a **legacy Claude project**, also add `ANTHROPIC_API_KEY`, or use `CLAUDE_CODE_OAUTH_TOKEN` (which takes precedence). Bedrock has its [own setup](/latest/providers/aws-bedrock).

    For an **all-Codex configured project**, skip the Anthropic secrets. You will add the managed OpenAI credential after creating the project mapping.

    See [Environment variables for AI-Implement](/latest/configuration/environment-variables) for more detailed information on each variable.
  </Step>

  <Step title="Install the GitHub App on the target repo">
    In your GitHub App settings, install the app on the target repository. This gives the orchestrator permission to dispatch workflows and the workflow permission to push branches and open PRs.
  </Step>

  <Step title="Install dependencies and start the orchestrator">
    Install packages and start the development server:

    ```bash
    npm install
    npm run dev
    ```

    The orchestrator starts polling for new issues and serving HTTP on port 8080. You should see log output confirming both.

    <Tip>
      Want to run the entire loop on your own machine? `npm run dev:local` executes ordinary jobs locally instead of on GitHub Actions — the orchestrator still polls your ticketing system and opens pull requests. See [Local development](/latest/setup/deploy#local-development) for what it needs and when to use it.

      For a configured Codex smoke, follow the [local Codex procedure](/latest/customize/local-harness#run-codex-with-an-external-configuration). Local Docker does not provide the managed GitHub Actions review-fix path.

      `npm run dev:run` is the smaller one: a single task read from a file, with no ticketing system and no orchestrator involved. See the [local harness](/latest/customize/local-harness).
    </Tip>
  </Step>

  <Step title="Create a project mapping in the admin UI">
    Open the admin UI at [http://localhost:8080/admin](http://localhost:8080/admin) and enter your `ADMIN_ACCESS_CODE`.

    Click **Configure → Projects → + New project** to open the stepper. Fill in the ticketing and source fields first.

    <Tabs>
      <Tab title="Linear">
        - **Ticketing System** — `Linear`
        - **Ticketing Config → Linear Team Key** — your Linear team's identifier (e.g. `ENG`)
        - **Source → GitHub Owner** — the GitHub org or user (e.g. `your-org`)
        - **Source → Repository Name** — the repository name (e.g. `your-repo`)
        - **Source → Default Branch** — the repo's primary branch (e.g. `main`). Must match the repo exactly.
      </Tab>

      <Tab title="Jira">
        - **Ticketing System** — `Jira`
        - **Ticketing Config → JQL** — a JQL clause that scopes which Jira issues this project mapping watches (e.g. `project = ACME`)
        - **Ticketing Config → Repo Field Value** — the value of the `AI-Implement Repo` field for issues belonging to this project mapping (e.g. `your-org/your-repo`)
        - **Source → GitHub Owner** — the GitHub org or user (e.g. `your-org`)
        - **Source → Repository Name** — the repository name (e.g. `your-repo`)
        - **Source → Default Branch** — the repo's primary branch (e.g. `main`). Must match the repo exactly.
      </Tab>
    </Tabs>

    <Warning>
      Nothing checks the default branch name against the repository when you save. A default branch name that does not exist saves cleanly and fails the run at its first step, when the runner tries to clone it.
    </Warning>

    Choose **GitHub Actions** as the runner for this Codex path. Complete the remaining project fields, then click **Create project**. Stage settings are added after the project exists.
  </Step>

  <Step title="Review and merge the workflow pull request">
    Creating the project mapping opens a pull request in your target repo containing `claude-implement.yml`, `claude-plan.yml`, and starter `WORKFLOW.md` and `PLANNING.md` files.

    Merge it before continuing — the workflows have to be on the default branch for AI-Implement to dispatch them.

    Check that the [runner image supports Codex](/latest/customize/runner-image). For an existing project, use **Sync workflows** and merge the update before continuing.

    The workflows open pull requests using the GitHub App credentials. The **Allow GitHub Actions to create and approve pull requests** setting is not required.
  </Step>

  <Step title="Add your OpenAI account">
    To use Codex, open **Models & providers** as an administrator. [Create a Codex account profile](/latest/providers/openai#account-profiles), permit it for the new project, then set an OpenAI API key or connect your own ChatGPT plan. Follow that guide's readiness checks before continuing.

    Skip this step and the next if you are keeping the project on legacy Claude behavior.
  </Step>

  <Step title="Choose the agents and opt the project in">
    Follow [Agent settings per stage](/latest/configuration/agents) to fill **Orchestrator stage defaults**, then set **Settings → Orchestrator Agent Defaults → Defaults mode** to `configured`.

    For an all-Codex setup, select `codex`, `openai`, an available model, the permitted OpenAI profile, and an elapsed timeout for all three stages. Setting defaults does not enroll a project.

    On **Projects**, open **Edit → Agents** for the saved project. Check the effective values, select **Opt in to stage agent configuration**, and click **Save agent settings**. If readiness refuses the save, use the [troubleshooting guide](/latest/reference/troubleshooting).
  </Step>

  <Step title="Create the trigger in your ticketing system">
    <Tabs>
      <Tab title="Linear">
        Follow [Prepare the Linear labels](/latest/setup/linear-app#prepare-the-linear-labels) before your first run. Create the pickup label (`AI-Implement` by default) and the workspace-level `Ready for Review` label. AI-Implement creates the other lifecycle labels automatically.
      </Tab>

      <Tab title="Jira">
        Create the two required custom select fields in your Jira instance: 
        - `AI-Implement Status` (with the accompanying status options)
        - `AI-Implement Repo` (with one option per mapped repo).
        
        <Note>
          See [Jira manual setup](/latest/setup/target-repo#jira-manual-custom-field-setup) for the full step-by-step.
        </Note>
      </Tab>
    </Tabs>

  </Step>

  <Step title="Mark an issue and watch the PR appear">
    <Tabs>
      <Tab title="Linear">
        In your Linear workspace, open any issue in the team you mapped and add the `AI-Implement` label.
      </Tab>

      <Tab title="Jira">
        Open any issue matched by your mapping's JQL and set its `AI-Implement Status` to `Ready`.
        
        <Warning>
          Make sure the issue's `AI-Implement Repo` field is set to the same value you entered in the mapping.
        </Warning>
      </Tab>
    </Tabs>

    On the next eligible poll, the orchestrator picks it up, marks it in progress, and dispatches the GitHub Actions workflow. Planning runs first if enabled. The selected implementation agent reads `WORKFLOW.md` and changes the code; the pipeline pushes the branch and opens a PR.

    When the run finishes, the issue is marked ready for review (Linear: `Ready for Review` label; Jira: `AI-Implement Status = PR Ready`), and the PR has an automated review comment on its merge readiness.

    <Tip>
      If nothing happens after 60–90 seconds, check the orchestrator logs in your terminal. The most common causes are a missing project mapping, incorrect ticketing credentials (`LINEAR_CLIENT_ID` and `LINEAR_CLIENT_SECRET`, or `JIRA_TOKEN`), or a GitHub App that isn't installed on the target repo.
    </Tip>
  </Step>

  <Step title="Verify the agent and result">
    [Check the run evidence](/latest/how-it-works#verify-the-agent-and-result), including **Reports → Agent attribution**, the PR's harness/model/provider footer, and the review outcome. Saved defaults alone do not prove which agent ran.

    The attribution card shows the latest invocation per job, not whole-job token or cost totals. An unavailable cost does not mean the run was free.
  </Step>

</Steps>
