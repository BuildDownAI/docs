---
title: "Configure project mappings"
description: "How to configure project mappings in the admin UI, including ticketing provider, concurrency limits, execution mode, session mode, and Claude provider settings."
---

A **project mapping** connects a ticketing-system scope (a Linear team or a Jira JQL clause) to a target GitHub repository and controls exactly how AI-Implement dispatches and runs implementations for that scope. Each mapping is stored in the orchestrator's SQLite database and can be created, edited, or deleted through the admin UI at `/admin`. You need at least one mapping for the orchestrator to do any work.

<Note>
  The **New project** stepper doesn't expose every field. These are set afterwards, by opening the project's **Edit** dialog:

  - `workflowFile` and `branchPrefix` — under [Source](#source) below
  - `extraEnv` — under [Runner](#runner)
  - `planningWorkflowFile` — under [Planning](#planning)
  - `maxTurns`, `maxIterations`, and `maxJobMinutes` — under [Capacity](#capacity)

  `paused` comes from neither dialog — it's the **Pause** / **Resume** button on the project's row.
</Note>

## Ticketing

<ParamField body="ticketingProvider" type="string" default="linear">
  The ticketing system this mapping watches for issues. Accepted values: `linear` or `jira`. The orchestrator can mix Linear and Jira mappings within a single deployment; each mapping picks one provider.
</ParamField>

<ParamField body="teamKey" type="string" required>
  Identifier for the ticketing scope this mapping watches.

  - For **Linear**, use your team's identifier — the short prefix shown in issue numbers, e.g. `ENG` in `ENG-42`. The orchestrator matches polled issues to this repo by that key.
  - For **Jira**, choose any label you like. Jira has no equivalent team concept, so the `jql` clause in `ticketingConfig` does the scoping instead.
</ParamField>

<ParamField body="ticketingConfig" type="object">
  Provider-specific configuration for issue discovery. The shape depends on `ticketingProvider`:

  ```json
  // For Linear (no extra fields required):
  { "kind": "linear" }

  // For Jira:
  {
    "kind": "jira",
    "jql": "project = ACME",
    "repoFieldValue": "your-org/your-repo",
    "statusFieldOverride": "customfield_10500",
    "repoFieldOverride": "customfield_10501",
    "profilesFieldOverride": "customfield_10502"
  }
  ```

  The extra configuration fields for Jira are used as follows:
  - `jql` scopes which issues this mapping watches.
  - `repoFieldValue` is the option value of the `AI-Implement Repo` custom field.
  - The three `…Override` fields are optional `customfield_NNNNN` IDs you only need to set when Jira auto-discovery by name is ambiguous — for the status field, the repo field, and the multi-select **AI-Implement Profiles** field respectively. Setting all three skips auto-discovery entirely. Leaving `profilesFieldOverride` unset while the field's name is ambiguous or non-default means profiles silently never populate for issues in this mapping.
  
  <Info>
    See [Jira manual custom-field setup](/setup/target-repo#jira-manual-custom-field-setup) for more detailed information.
  </Info>
</ParamField>

## Source

<ParamField body="owner" type="string" required>
  GitHub organization name or username that owns the target repository (e.g. `my-org`).
</ParamField>

<ParamField body="repo" type="string" required>
  Name of the target GitHub repository (e.g. `my-api`). Combined with `owner`, this tells the orchestrator where to dispatch workflow runs.
</ParamField>

<ParamField body="defaultBranch" type="string" required>
  Branch that Claude creates pull requests against. It must match the repository's actual primary branch, commonly `main`, `master`, or `development`.
</ParamField>

<ParamField body="branchPrefix" type="string">
  Extra path segment prepended to every branch this project creates. Set it to `pr` and a branch that would have been `ai-implement/…` becomes `pr/ai-implement/…`.

  <Tip>
    Useful when a repo's branch protection or CI rules key off a particular prefix. Leave unset for no prefix.
  </Tip>
</ParamField>

<ParamField body="workflowFile" type="string" default="claude-implement.yml">
  Name of the GitHub Actions workflow file to dispatch for implementation runs. Change the default only if you've renamed or customized the workflow file in the target repo.
</ParamField>

<ParamField body="skillsRepo" type="string">
  Repository of skills to make available to Claude during this project's runs, as an `owner/repo` shorthand or an `https://github.com/...` URL. Cloned into the workspace before implementation begins.

  Leave unset to run without project skills. This setting covers `/ai-implement` comment-triggered runs as well.

  <Warning>
    Nothing else is accepted. An SSH remote, or a URL on any other host, is rejected when you save — the clone authenticates with a GitHub token, and that credential must never be sent elsewhere.
  </Warning>
</ParamField>

<ParamField body="dependencyTokenScope" type="string">
  Grants each run read access to repositories beyond the one it is working in, so a build that pulls a private sibling repository as a dependency can fetch it.

  - Left unset (the default), the feature is off, and a run can read only its own target repository.
  - Set to `installation`, the run receives a token covering every repository the installed GitHub App can see.

  That grant is all-or-nothing and read-only: it cannot be narrowed to a chosen subset of repositories, and it never permits writing or pushing to any of them.
</ParamField>

<ParamField body="sensitiveAddPatterns" type="array">
  Extra glob patterns treated as sensitive for this project, on top of the built-in list. A run that stages a matching file is blocked before it commits — see [Blocked by a security guardrail](/reference/run-statuses#blocked-by-a-security-guardrail).

  <Note>
    Patterns match against both the full path and the file name, so `*.pem` catches `certs/server.pem`.
  </Note>
</ParamField>

<ParamField body="sensitiveAllowPatterns" type="array">
  Glob patterns exempted from the sensitive-files check for this project. Useful for a fixture or example file whose name resembles a real credential.

  <Warning>
    Allow patterns are checked first and override the built-in list as well as your own additions — a file matching one is never blocked. Keep this list as narrow as you can.
  </Warning>
</ParamField>

## Runner

<ParamField body="executionMode" type="string" default="github-actions">
  Where implementation runs execute.

  - `github-actions` — Claude runs inside a standard GitHub Actions job in the target repo. No additional infrastructure required.
  - `fly-machines` — Claude runs inside a Fly Machine launched by the orchestrator. Requires the Fly sessions app to be configured.
</ParamField>

<ParamField body="sessionMode" type="string" default="autonomous">
  How the Claude session behaves during a run.

  - `autonomous` — Claude works to completion without human interaction.
  - `interactive` — Claude pauses and waits for feedback at decision points.
  - `hybrid` — Claude proceeds autonomously but surfaces questions when it is uncertain.
</ParamField>

<ParamField body="machineCpus" type="number" default="2">
  Number of CPUs allocated to the Fly Machine for each run. Only applies when `executionMode` is `fly-machines`.
</ParamField>

<ParamField body="machineMemoryMb" type="number" default="4096">
  Memory allocated to the Fly Machine in megabytes. Only applies when `executionMode` is `fly-machines`. Minimum: `256`.
</ParamField>

<ParamField body="extraEnv" type="object">
  A flat key-value object of additional environment variables to inject into the Fly Machine environment at dispatch time. Only applies when `executionMode` is `fly-machines`. Example: `{"DATABASE_URL": "postgres://..."}`.
</ParamField>

## Claude provider

<ParamField body="provider" type="string" default="anthropic">
  The Claude provider used by the dispatched workflow.

  - `anthropic` — Uses the Anthropic API or Claude Code OAuth token, whichever is configured as an org secret in the target repo.
  - `bedrock` — Uses AWS Bedrock via GitHub OIDC. Requires `awsRegion` to also be set.
</ParamField>

<ParamField body="awsRegion" type="string">
  AWS region that hosts your Bedrock inference profile (e.g. `us-west-2`). Required when `provider` is `bedrock`. Ignored for the `anthropic` provider.
</ParamField>

<Note>
  `provider=bedrock` is not supported when `executionMode` is `fly-machines`. Use `executionMode=github-actions` for Bedrock runs.
</Note>

## Planning

<ParamField body="planningEnabled" type="boolean" default="true">
  Whether to run a planning phase before implementation. When enabled, the orchestrator dispatches the planning workflow first, Claude posts structured analysis to the issue, and then implementation proceeds.
  
  See [AI planning phase](/configuration/planning) for details.
</ParamField>

<ParamField body="planningWorkflowFile" type="string" default="claude-plan.yml">
  **Required** when `planningEnabled` is `true`.
  
  Name of the GitHub Actions workflow file dispatched for the planning phase.
</ParamField>

<ParamField body="autoApprovePlans" type="boolean" default="true">
  Reserved for a future manual-approval gate. It does **not** currently affect dispatch behavior — implementation always starts automatically once planning succeeds, whatever this is set to.

  See [AI planning phase](/configuration/planning) for what actually happens between the two phases.
</ParamField>

<ParamField body="autoMerge" type="boolean" default="false">
  <Warning>
    Nothing reads this setting. It is stored on the mapping and offered in the admin interface, but no code path consults it, so turning it on or off changes nothing.
  </Warning>

  Child pull requests are merged into their grouping branch whatever it is set to. [Merging child pull requests](/reference/feature-branch-grouping#merging-child-pull-requests) covers the conditions that do apply, and what still waits for a human.
</ParamField>

## Capacity

<ParamField body="maxInProgressAiIssues" type="number" default="3">
  Maximum number of AI implementation runs that can be in progress simultaneously for this team. If the limit is reached, newly eligible issues are held until a slot opens.
</ParamField>

<ParamField body="maxTurns" type="number" default="50">
  Cap on Claude conversation turns per implement pass. Applies to both Anthropic and Bedrock providers.

  Lower values surface decisions earlier and cut cost; higher values let Claude work through harder problems without aborting mid-pass.
</ParamField>

<ParamField body="maxIterations" type="number" default="3 (Anthropic), 2 (Bedrock)">
  Cap on implement/review cycles in the feedback loop. The Bedrock default is lower for provider reliability.

  Each iteration is one `implement` → `review` pass; the cycle stops early when review approves the diff.
</ParamField>

<ParamField body="maxJobMinutes" type="number" default="90">
  Cap on the GitHub Actions job timeout in minutes. GitHub Actions execution mode only — Fly Machines and local Docker have no equivalent timeout.
</ParamField>

<Tip>
  These caps cover `/ai-implement` comment-triggered gap-fill runs as well — there is no separate per-repo setting to keep in step with them.
</Tip>

## Lifecycle

<ParamField body="paused" type="boolean" default="false">
  When `true`, the orchestrator skips this mapping during polling — no planning runs, no implementation dispatches, no gap-fill triggers. Existing in-flight runs continue, but no new work is picked up until you unpause. 
  
  Useful for temporarily disabling a mapping without deleting and recreating it.
</ParamField>
