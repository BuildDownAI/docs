title: "Customize PLANNING.md for your codebase"
description: "How to customize PLANNING.md: control what Claude explores before each implementation run, and what the planning comments it posts to your ticketing system contain."
---

`PLANNING.md` controls what Claude does during the planning phase. When the planning workflow (`claude-plan.yml`) runs for an issue, it renders this file and sends the result to Claude as the prompt.

Claude explores the repo read-only and writes planning comments back to the issue, without creating any branches, files, or pull requests.

## File structure

Like `WORKFLOW.md`, `PLANNING.md` has two parts:

**YAML front matter** (between the `---` lines at the top) — read by the workflow to configure the run. Stripped before Claude sees anything.

**Markdown body** — everything after the front matter. A fixed list of variables is substituted into it, and the result is sent to Claude as the prompt.

## Front matter keys

<AccordionGroup>
  <Accordion title="model">
    The model ID passed to `claude-code --model`. Accepts any ID your configured provider supports.

    ```yaml
    # Anthropic API or OAuth
    model: claude-sonnet-4-6

    # AWS Bedrock (replace with your model ID or inference-profile ARN)
    model: anthropic.claude-sonnet-4-6-20250805-v1:0
    ```

    This key is **required when using Bedrock**. There is no Bedrock-specific default — the model resolves from a single provider-agnostic chain that ends in `claude-sonnet-4-6`.

    Omit it on a Bedrock-mapped repo and that Anthropic model ID is substituted silently. It is invalid on Bedrock, so the run fails when the model is invoked rather than up front.

    For the Anthropic provider, `claude-sonnet-4-6` is the intended default and omitting the key is safe.
  </Accordion>
</AccordionGroup>

## Variables available in the body

The variables below are substituted into the body by a regular expression, not by `envsubst`. Reference any of them anywhere in the body.

<Note>
  Only `${NAME}` forms are substituted, and a token that is not on this list is treated differently than shell semantics would suggest. [Workflow template files](/configuration/workflow-templates) covers the rules and what they mean for a shell example in your body.
</Note>

| Variable | Description |
|---|---|
| `${ISSUE_IDENTIFIER}` | Ticketing-system identifier — `ENG-42` for Linear, `PROJ-42` for Jira |
| `${ISSUE_TITLE}` | Issue title |
| `${ISSUE_DESCRIPTION}` | Full issue description (Markdown) |
| `${ISSUE_ID}` | Issue UUID — used in API calls to post comments |
| `${PARENT}` | Parent issue as `- IDENTIFIER: Title`, or `None` |
| `${SIBLINGS}` | Sibling stories (other children of the same parent), newline-separated, or `None` |
| `${DEPENDENCIES}` | Related issues as `- [type] IDENTIFIER: Title`, newline-separated, or `None` |

## Comment types Claude must post

Claude writes every one of the following as its own comment on your ticketing issue. The headers are exact strings the implementation workflow uses to locate planning context later, so do not change them.

### Implementation Map

Header: `## 🗺 AI Planning: Implementation Map`

Written for whoever implements the issue, and capped at 60 lines.

Required sections in this comment:

- **Approach** — at most three sentences describing the implementation strategy
- **Files** — one bullet per file, each opening with `Create:`, `Modify:`, `Test:` or `Delete:` followed by a backtick-quoted path
- **Constraints & Hazards** — load-bearing tests, generated files, migration ordering, and integration seams the implementer must not break

Cross-story coordination belongs in **Constraints & Hazards** when `${DEPENDENCIES}`, `${SIBLINGS}` or `${PARENT}` is not `None`, rather than in a comment of its own.

<Warning>
  The **Files** bullets are parsed, not just read — the orchestrator uses them to hold back a sibling issue whose declared files overlap this one's.

  A bullet counts only when it uses one of those four verbs and quotes its path in backticks. Anything else parses to nothing, and an empty result fails open: the run dispatches anyway, silently without that protection.
</Warning>

The comment ends with a machine-readable block:

```markdown
<!-- ai-implement-planning
v: 1
files: ["src/a.ts", "src/b.ts"]
risk: low|medium|high
-->
```

### Acceptance Bar

Header: `## ✅ AI Planning: Acceptance Bar`

Written for the reviewer, and handed to the review pass so it has something falsifiable to check the diff against.

A numbered list of claims, each one checkable against the diff or by running a named command. A generic enumeration doesn't qualify — "all tests pass" is not a claim.

```markdown
1. `parseDeclaredFiles` returns a non-empty set for a Modify bullet.
2. `npm test` exits 0 with at least six passing cases for the planning fetch.
3. `src/pipeline/steps/implement.ts` contains no reference to `WorkUnit`.
```

### Risks & Open Questions

Header: `## ⚠️ AI Planning: Risks & Open Questions`

Written for the implementer and the reviewer both.

Edge cases, unknowns, and problems found while exploring the codebase, grounded in what Claude actually found rather than generic boilerplate.

## Customizing the "Repo context" section

The `## Repo context` section is where you point Claude at the right parts of your codebase and establish the conventions that matter for architectural decisions.

```markdown
## Repo context

- **Stack:** Node.js 20, TypeScript 5, PostgreSQL 16, Prisma ORM, Vitest
- **Key conventions:**
  - All database access goes through the repository layer in `src/repositories/`
  - API routes live in `src/api/routes/`; middleware in `src/api/middleware/`
  - Avoid introducing new dependencies without good reason
- **Areas to always check:** `src/models/`, `src/api/`, `migrations/`
```

<Tip>
  Use the **Areas to always check** field to direct Claude to the directories most likely to be relevant for any given issue. This reduces analysis time and keeps the architecture comments grounded in your actual code structure rather than generic advice.
</Tip>

## Example: adding analysis prompts

You can add repo-specific analysis instructions anywhere in the body. For example, to always have Claude check the migration directory when database changes are involved:

```markdown
## Repo context

- **Areas to always check:** `src/models/`, `src/api/`, `migrations/`
- If the issue involves data changes, check `migrations/` for the latest schema
  and assess whether a new migration is needed.
```

<Note>
  The sync workflow seeds `PLANNING.md` into your repo once and never overwrites it. Every change you make is permanent — future syncs will not touch this file.
</Note>
